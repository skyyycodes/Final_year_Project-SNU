\chapter{Introduction}

\section{Context of the Study}

Digital files can be copied, shared, and edited very easily. Because of this, protecting ownership of digital content has become an important problem in computing. A single project may include an image, an audio clip, a text document, and sometimes a video. In many cases, the owner may want to attach hidden ownership information to each of these files. The two common ways to do this are \emph{digital watermarking} and \emph{steganography}~\cite{cox2007digital,petitcolas1999information,johnson1998exploring}. In digital watermarking, identifying information is placed inside the file so that ownership or authenticity can later be checked. In steganography, the aim is to hide the message itself so that the communication is not obvious.

These two ideas have different goals, but they often use similar techniques. Both take advantage of the fact that small changes in pixels or audio samples are usually not noticed by human eyes or ears. For this reason, least-significant-bit (LSB) methods are widely used in simple watermarking and steganography systems~\cite{chan2004hiding,bender1996techniques,morkel2005overview}. LSB methods are easy to understand and fast to implement, but they are not very strong when the file is compressed or changed. Transform-domain methods are usually stronger, but they are also harder to build and explain.

Most existing systems work on only one file type and usually insert only one watermark into one cover file. In practice, this is often not enough. A user may want to add different watermarks for different receivers, versions, or release groups. The same work may also need to be protected across image, audio, and text files together. Existing tools do not handle this situation well, so users often depend on multiple separate tools.

Adding multiple watermarks to the same LSB cover file is not simple. If the embedding position is fixed, one watermark can overwrite another. In many systems, the password is used only for basic encryption and not for choosing where the watermark will be stored. Collision detection is also often missing. On top of that, the payload format usually changes from one file type to another. Because of these problems, this work focuses on a simple framework that uses a password-based location strategy for images and a common payload format across image, audio, text, and video.

The project is also motivated by a practical classroom problem. Many student projects and small software tools are either too narrow or too complex. Some tools support only images. Others require several libraries, command-line knowledge, or a full understanding of signal processing before a user can even test a basic watermark. That makes them difficult for beginners. We wanted to build something that is small enough to understand, but still broad enough to show how one framework can handle different file types in a consistent way.

Another reason for choosing this topic is that ownership problems do not appear only in large companies or media houses. Even in student work, design files, notes, lab documents, presentation media, and small video clips are shared frequently. Once a file leaves the original owner, it becomes hard to prove where it came from unless some identifying information is already attached to it. A visible watermark is not always desirable because it changes the appearance of the content. Hidden watermarking is therefore a useful middle ground for controlled sharing scenarios.

This dissertation does not claim to solve every security problem in multimedia protection. Instead, it takes a modest and clear goal: build a unified prototype that is easy to explain, easy to test, and strong enough to demonstrate the main design ideas. That focus is important. A simpler system is easier to verify, easier to present, and easier to improve later.

\section{Objectives}

This project aims to:

\begin{enumerate}[label=\textbf{O\arabic*.}]
    \item Design and implement a row-based least-significant-bit watermarking algorithm for $256 \times 256$ BMP images that allows up to \textbf{256 independent watermarks} to exist in the same cover image, with each watermark linked to its own password.
    \item Use the password not only as a secret input, but also as a way to choose the image row and starting column where the watermark will be stored.
    \item Extend the same overall idea to three more carrier types: WAV audio, plain-text files, and video.
    \item Build one graphical user interface so that the user can work with all four media types without learning a different workflow each time.
    \item Store a timestamp with every watermark so that extraction can recover both the hidden text and the time of embedding.
    \item Keep the implementation readable and well logged so that the project is useful both as a working prototype and as a learning tool.
\end{enumerate}

Taken together, these objectives balance two needs. The first is functionality: the system should work across multiple media types. The second is clarity: the internal logic should stay simple enough that another student can read the code, follow the data flow, and understand why the result works.

\section{Scope and Organization}

This dissertation is organized into six chapters. Chapter~\ref{Literature_Survey} presents a critical, carrier-domain literature review of digital watermarking and steganography. Chapter~\ref{Problem_Identification} defines the precise research gap, the formal problem statement, the threat model under which the system is designed, the research hypotheses, and the resulting design constraints. Chapter~\ref{Proposed_Methodology} details the end-to-end methodology, including the system architecture, the password-to-location mapping, the row-occupation marker, the per-pixel 3--3--2 bit split, the audio, text and video extensions, the common payload format, and the evaluation metrics used to compare the proposed system with the literature. Chapter~\ref{Experimental_results} reports implemented results for each module on a representative set of cover files, contrasts the proposed system with single-modality LSB baselines, and clearly separates implemented experiments from future work. Chapter~\ref{Conclusion_and_Future_Work} concludes the dissertation, summarizes the lessons learned, and outlines a roadmap of future improvements such as stronger cryptographic primitives, support for arbitrary image sizes, and resilience against geometric and lossy-compression attacks.

\section{Contributions}

The contributions of this work are summarized as follows:

\begin{enumerate}[label=\textbf{C\arabic*.}]
    \item \textbf{A simple review of the real gap.} The literature survey shows that many systems are strong in one medium only, while support for both multiple watermarks and multiple carrier types is still uncommon.
    \item \textbf{A row-based, password-linked image method.} The image algorithm treats each row of a $256 \times 256$ BMP image as a possible watermark slot. The password decides where the watermark starts, which helps distribute different watermarks across the image.
    \item \textbf{An overwrite check before embedding.} A sentinel marker is written at the beginning of an occupied row. This gives the system a simple way to detect that a row is already in use and stop a second embedding before data is overwritten.
    \item \textbf{A lightweight 3--3--2 RGB encoding rule.} Each character is split across the red, green, and blue channels of one pixel. The visual change stays small, but extraction remains straightforward.
    \item \textbf{One framework for four media types.} The project combines image, audio, text, and video handling inside one Java Swing application instead of treating them as four unrelated tools.
    \item \textbf{One shared payload format.} All modules use a consistent start marker, separator, timestamp field, and end marker. This keeps the extraction logic similar across different file types.
    \item \textbf{A reproducible student-level prototype.} The implementation is direct enough to run, test, explain, and extend without depending on a large external software stack.
    \item \textbf{A didactic implementation with logs.} The software prints the main internal steps in its log window, which makes the project easier to demonstrate and easier for another student to study later.
\end{enumerate}
